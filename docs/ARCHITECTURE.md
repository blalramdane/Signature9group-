# المعمارية التقنية المقترحة — Signature 9 Real Estate

## المبدأ
تطبيق داخلي عربي لإدارة العقارات، مصمم للموبايل والكمبيوتر، مع فصل واضح بين الواجهة وواجهات البرمجة وقاعدة البيانات والتخزين. هذه وثيقة مقترحة وليست وصفًا لكود موجود؛ يتم تثبيت الإصدارات بعد فحص البيئة قبل بدء الإنشاء.

## المكونات
- **Frontend:** React + TypeScript، RTL افتراضي، واجهات متجاوبة، وPWA.
- **Backend:** Laravel API مع تحقق مركزي من المدخلات والصلاحيات.
- **Database:** MySQL في البيئة المشتركة، مع migrations وقيود وفهارس واضحة.
- **Media storage:** تخزين ملفات مستقل عن بيانات العقار، مع روابط محمية وسياسة تحقق من الملفات.
- **Offline layer:** تخزين محلي منظم وطابور عمليات معلّق، مع مؤشرات مرئية للمستخدم.
- **Testing/CI:** اختبارات تلقائية وفحوص تنسيق وبناء قبل دمج التغييرات.

## توافق الإصدارات
لا نفترض إصدارًا رئيسيًا قبل فحص PHP وNode وComposer في الجهاز المستهدف. يجب اختيار Laravel وإصدارات أدواته بما يتوافق مع البيئة المعتمدة، وتوثيق طريقة تثبيت متكررة. لا تحفظ أسرارًا في ملفات Git؛ استخدم `.env.example` بقيم توضيحية فقط.

5. المتابعات والملاحظات وسجل النشاط.
6. البحث والفلاتر والتقارير.
7. الاستيراد والتصدير.

9. مساعد استخراج المعلومات لاحقًا.

## نموذج العقار
حقول مقترحة: معرف عام ثابت، رقم مرجعي بشري، نوع المعاملة (بيع/إيجار)، نوع الوحدة، المحافظة/المدينة/المنطقة، عنوان وصفي، مساحة، سعر وعملة، تفاصيل التشطيب، غرف/حمامات عند انطباقها، وصف، حالة العمل، مصدر البيانات، مسؤول التسويق، مالك/جهات الاتصال، تواريخ الإنشاء والتحديث، والحذف المنطقي عند الحاجة.

يجب فصل **نوع المعاملة** عن **حالة العقار**. حالات أولية ممكنة: مسودة، متاح، قيد التفاوض، محجوز، تم التعاقد، غير متاح، مؤرشف. تُعتمد المسميات النهائية مع فريق الشركة، ويجب حفظ سجل تغيّر الحالة.

## API ومبادئ التطبيق
- إصدارات API واضحة عند الحاجة.
- تحقق من المدخلات وتطبيع القيم على الخادم.
- قوائم ونتائج البحث مقسمة إلى صفحات.
- بحث وفلاتر عبر حقول محددة وفهارس مناسبة.
- استجابات أخطاء مفهومة دون تسريب معلومات داخلية.
- تفويض لكل عملية قراءة أو تعديل أو تنزيل ملف.
- سجل تدقيق للعمليات الحساسة.
- لا يثق الخادم بمعرّف مستخدم أو دور مرسل من المتصفح.

## استراتيجية الملفات
- قيود امتداد ونوع وحجم، وتوليد أسماء ملفات داخلية آمنة.
- حفظ بيانات وصفية للملف في `property_media`.
- عدم جعل مجلد الملفات عامًا إن كانت الصور أو الوثائق حساسة.
- التحكم في التنزيل بحسب الصلاحيات.
- وضع سياسة احتفاظ ونسخ احتياطي للمرفقات.

## Offline والمزامنة
تُنفّذ Offline على مراحل حتى لا يتم الادعاء بوجود مزامنة موثوقة قبل اختبارها.

1. تخزين بيانات القراءة المطلوبة محليًا.
2. تخزين تعديل المستخدم كعملية ذات معرف idempotency ثابت.
3. إظهار الحالة: محليًا، في انتظار المزامنة، تمت المزامنة، أو تحتاج مراجعة.
4. عند الاتصال، إرسال العمليات مع إعادة المحاولة دون تكرار الأثر.
5. مقارنة إصدار السجل/تاريخ تعديله قبل تطبيق التحديث.
6. عند التعارض، عدم الكتابة فوق البيانات بصمت؛ إظهار الاختلافات والسماح بقرار واضح أو سياسة دمج معتمدة.
7. العمليات الحساسة مثل الصلاحيات والحذف النهائي لا تُنفذ محليًا دون تحقق من الخادم.

يلزم اختبار إغلاق المتصفح، امتلاء التخزين، انتهاء الجلسة، تحديث نسخة التطبيق، وتعديل نفس السجل من جهازين.

## الإدخال بمساعدة OCR/AI
- يبدأ كأداة اقتراح لا ككاتب تلقائي.
- يحفظ مرجع مصدر الرسالة/الصورة بحسب سياسة الخصوصية.
- يعرض الحقول المستنتجة للمعاينة والتعديل.
- يتعامل مع البيانات غير المؤكدة على أنها فارغة/غير مؤكدة لا كحقائق.
- يتطلب اعتمادًا صريحًا قبل إنشاء سجل أو تغييره.
- يختبر على بيانات اصطناعية أو منقحة قبل أي بيانات عملاء فعلية.

## أمن وخصوصية
- كلمات المرور تُدار بتخزين آمن عبر إطار العمل؛ لا تُكتب في السجلات.
- حماية من محاولات الدخول المتكررة، وCSRF/CORS وفق نمط النشر، والتحقق من الجلسات.
- أقل صلاحية ممكنة للمستخدمين والخدمات.
- أسرار التطوير والإنتاج منفصلة.
- سجل تدقيق لا يحتوي على كلمات مرور أو محتوى حساس غير ضروري.
- نسخ احتياطي دوري، اختبار استعادة، وتوثيق آلية تدوير الأسرار.
